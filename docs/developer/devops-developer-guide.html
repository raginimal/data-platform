Developer guide

Developer DevOps Golden Path

As a developer, what do I do from starting a feature to safely getting it into production? Consistent software development and DevOps practices for AI projects, with AI-specific engineering practices where they add value.

DEVELOPER ACTIONSCI ENFORCESAGENTS ADVISEHUMANS DECIDEPHASES 1-6
01 — Purpose

Why this guide exists

The policies in policies/ say what must be true. This guide says what you do. It turns the AI Engineering Golden Path into a developer routine so the correct engineering path is the easiest path.

Problem

Rules without a routine

Policies, CI and review contracts exist, but a developer still has to know which to use, and when.

Solution

One path, in order

Branch, build, validate, review, release, roll back. Each step names the command, the check and the owner.

Relationship

Built on the Golden Path

It adds no phase, agent or check. Authoritative detail stays in the existing docs, linked throughout.

Choose your adoption path

Greenfield and Brownfield are separate paths. Pick one; the guide below adapts.

Greenfield — build right from day one

A new AI project starts from the skeleton and follows the Golden Path from the first commit.

Brownfield — assess and improve

An existing project is not rebuilt. The skeleton is a reference standard for assessment and progressive adoption.

02 — Golden Path at a glance

The whole path on one screen

Green steps are deterministic CI, red are advisory agents, amber are human decisions.

  3. PoliciesFind the policy IDs that apply under policies/ and list them in your PR.

  5. DevelopmentCode, tests, AI assets, configuration and IaC in small, reviewable steps.

  8. Pull requestComplete the PR template: risk, policy IDs, impact, testing, rollback.
  9. CIDeterministic gates run automatically and are authoritative.

  15. TEST / STAGINGPromoted after DEV validates; TEST/UAT is the TEST environment in this framework.

  17. PRODThe same verified artifact is deployed to production.
  18. Verification / rollbackValidate health and behavior. If it fails, roll back to the previous known-good artifact.
Manual process. The repository has no assessment tooling. Brownfield assessment is a guided checklist you run by hand against the existing policies; the skeleton is a reference, not something to copy over.
  1. Existing projectPick the repository and name an owner for the assessment.
  2. Repository assessmentDo README, AGENTS/CONTRIBUTING-style guidance, CODEOWNERS and protected main exist? Is everything in version control and free of secrets? (RP-*)
  3. Architecture assessmentAre boundaries, APIs, data contracts and decisions documented? Are there ADRs? Is infrastructure defined as code? (ARCH-*, ARCH-DEP-*)
  4. DevOps assessmentBranching, PR evidence, CI gates, build-once artifacts, environment separation, production approval, tested rollback. (DEVOPS-*)
  5. Security assessmentSecrets, IAM and least privilege, dependency and vulnerability handling. (SEC-*, SEC-SEC-*, SEC-IAM-*)
  6. AI engineering assessmentModel approval, prompt handling, evaluation evidence, guardrails, data classification and contracts. (AI-*, DATA-*)
  7. FindingsRecord each gap with the policy ID, evidence and owner.
  8. Risk / maturity assessmentRank findings using risk classification (Low to Critical). A simple maturity scale helps: 0 absent, 1 ad hoc, 2 documented, 3 enforced by a deterministic check. The scale is a suggestion, not a repository policy.
  9. Remediation roadmapOrder work by risk: secrets and protected main first, then CI gates, then architecture and AI practices.
  10. Progressive adoptionAdopt one policy area at a time. Time-bound gaps go through the exception process.

The rest of the guide describes the day-to-day developer path. It applies to a Greenfield project from day one, and to a Brownfield project as each area is adopted.

05 — Before you start coding

Five minutes that save a rework

Checklist

  • Understand the requirement and its work item
  • Identify the affected component
  • Check the architecture and the baseline
  • Check the applicable policy IDs
  • Check ownership in .github/CODEOWNERS
  • Note security, data and AI implications
  • Decide whether infrastructure changes
  • Create the feature branch

If you cross a boundary

  • New service, data store, public API, model or provider, RAG source, guardrail change, infrastructure pattern or breaking change: write an ADR (ARCH-007).
  • The Baseline Guard reports BASELINE_IMPACT or ARCHITECTURE_CHANGE for changes touching approved boundaries.
  • Higher-risk changes need the specialist owners in the approval matrix.
  • If a MUST cannot be met, use the exception process. Do not work around it.
06 — Branching strategy

Short-lived branches, protected main

A simple trunk-based model. Sources: .github/BRANCHING.md, DEVOPS-BR-001 to DEVOPS-BR-004.

Naming

feature/<issue>-<short-name>
bugfix/<issue>-<short-name>
hotfix/<incident>-<short-name>

Lifetime

One work item per branch, kept short. Merged branches are deleted; owners review stale ones.

Stay current

Rebase or update from main before merge when required checks depend on current main. Do not force-push shared branches without maintainer approval.

Hotfix

Must reference an incident or change record and follow the break-glass procedure if protections are bypassed.

Release branches

Not part of the default model. Add them only with an ADR and release-owner approval. This is not GitFlow.

Protected main

No direct development on main. Everything goes through a PR.

07 — Development

What good looks like while you build

Code
  • Small, modular, readable changes; follow the stack overlay
  • Handle errors explicitly; log without secrets or PII
  • Keep config out of code and secrets out of Git
  • Document changed interfaces and configuration
Tests
  • Unit tests for deterministic logic (tests/unit/)
  • Integration tests when a boundary changes (tests/integration/)
  • End-to-end tests when a workflow changes (tests/e2e/)
  • Do not lower coverage thresholds to pass
AI
  • Use the templates in ai/models, ai/prompts, ai/evaluations, ai/guardrails
  • No secrets or sensitive data in prompts
  • Show evaluation evidence for model, prompt, RAG or guardrail changes
  • AI-generated code gets the same tests, scans and review
Data
  • Classify data and know where PII is (DATA_POLICY.md)
  • Keep data contracts versioned (DATA-CON-*)
  • Use only approved test data; no production data in DEV or TEST
  • Declare data impact in the PR
Infrastructure
  • Production infrastructure as reviewed code (ARCH-006)
  • Keep DEV, TEST and PROD separate
  • Least privilege for identities and tokens (SEC-IAM-*)
  • State rollback for infrastructure changes

Do not hide failures, lower thresholds or treat an unavailable required check as passed. A check that cannot run reports NOT CONFIGURED. If a check fails on a clean main, tell the repository maintainer rather than working around it.
09 — Commit

Small, meaningful, safe

Rules

  • Conventional Commits: type(scope): imperative summary
  • Types: feat, fix, docs, test, refactor, build, ci, chore
  • One focused change; no unrelated edits
  • No secrets, generated output or temporary files
  • Traceable to the work item; keep commits reviewable

Examples

feat(summary): add customer summary endpoint
fix(rag): handle empty retrieval result
test(summary): cover missing customer id
docs(adr): record vector store decision
ci: pin checkout action version
10 — Pull request

A PR a reviewer can approve in one pass

Complete every relevant section of the PR template. Sections that do not apply need a reason.

Developer activityAutomated CIHuman approvalAgent finding (advisory)

What you do: branch from current main using feature/<issue>-<name>, build and test the change, run bash scripts/check.sh, then open a PR with the template completed. Fix CI failures and review comments on the same branch. The merge happens only after required checks pass and a required human approves; an agent recommendation alone is never enough.

Change

What changed, why, related work item.

Risk and applicability

Low, Medium, High or Critical; applicable policy IDs; required approvals.

Engineering impact

Architecture and API, configuration and infrastructure, data.

Testing

Output of bash scripts/check.sh; unit, integration and E2E evidence.

Security and AI impact

Secrets, IAM, dependencies; model, prompt, RAG, evaluation, guardrail changes.

Operations and governance

Deployment impact, post-deployment validation, rollback; ADR or exception link; baseline declaration; AI assistance used.

When an ADR is needed: a new service, external dependency, data store, public API, model or provider, RAG source, guardrail change, infrastructure pattern, security exception or breaking change. Normal feature work does not need one. If the Baseline Guard reports ARCHITECTURE_CHANGE, the ADR must set Baseline impact: change and list the boundaries.
11 — CI

What happens automatically

CI is responsible for deterministic enforcement. It is repeatable and authoritative. AI agents do not replace it and cannot override it.

WorkflowChecksStatus in the skeleton
ci.ymlBuild artifact; core repository validationCore
policy.ymlRepository structure and ownership, policy IDs, exceptions, PR governance, risk paths, architecture baseline impactCore
quality.ymlLint and testsConditional on stack overlay
security.ymlSecret scanning; dependency, container and IaC scanners when assets and scanners existSecrets: core. Others: conditional
infrastructure.ymlTerraform format and validationConditional on IaC assets
cd.ymlBuild once, verify, promote DEV, TEST, PRODRuns on version tags or manual dispatch

Baseline Guard

A script run by policy.yml on PRs. It classifies changes as NO_BASELINE_IMPACT, BASELINE_IMPACT or ARCHITECTURE_CHANGE and prints the reviews needed. It fails only when the ADR rule is not met and the baseline is approved; while the baseline is draft it warns.

Reading the result

NOT CONFIGURED means a stack-specific check does not exist yet. It is not a pass. Configure it in your stack overlay.

12 — Agents and skills

What to expect from the four agents

Agents are advisory and read-only. They select the relevant skills for the files you changed (routing: config/ai/agent-routing.yaml) and report findings with evidence, severity and a recommendation. The repository defines the contracts and routing; it does not include an autonomous agent runtime.

Architecture Agent
  • Architecture and boundaries
  • Dependencies
  • ADRs
  • Design trade-offs
Security & DevOps Agent
  • Security and IAM
  • Secrets
  • Infrastructure
  • CI/CD and deployment risk
AI Engineering Agent
  • Models and prompts
  • RAG
  • Guardrails and evaluations
  • AI-specific risk
Code Quality Agent
  • Maintainability
  • Tests and complexity
  • Duplication
  • Error handling

How the pieces fit

  • Policy = WHAT must be true
  • Skill = HOW a check is done
  • Agent = WHO reasons about it
  • Workflow = WHEN it runs
  • Human = ACCOUNTABILITY

What a finding looks like

Finding ID, agent and skill, severity, confidence, policy ID, file and line, evidence, recommendation, human action needed, and disposition. See docs/agent-output.md.

Your response

Fix it, or record a disposition with a reason: accepted, rejected, false-positive or resolved. A human reviewer owns the final call.

14 — Merge

When it is ready

CI passes+Required human reviews+Agent findings addressed+ADR / exception recorded where triggered+No unresolved blocking feedback=MERGE
  • Required checks and CODEOWNER or designated human approval are enforced by branch protection. The number of approvers is set by the administrator, not by this guide.
  • Agent findings are advisory, but each should be fixed or carry a recorded disposition. A merge is never justified by an AI recommendation alone.
  • Squash merge is the default. Delete the branch afterwards.
15 — Release and deployment

Build once, promote the same artifact

Short-lived branchMerge to mainRelease / CIDEV and TEST/UATHuman approval

What you do: keep branches short and merge through a PR, never directly to main. A release is a version tag on main (v*.*.*); the version numbers shown are illustrative. The CD workflow builds once and verifies the artifact before each stage, promoting DEV, then TEST/UAT, then PROD only after the human approval on the PROD environment. Check each environment after it deploys, and keep the release's commit, artifact digest and approver recorded.

Immutable artifact

bash scripts/build-artifact.sh creates the artifact with a manifest and SHA-256 digest. bash scripts/verify-artifact.sh checks it before every stage. Never rebuild per environment.

Environment separation

DEV, TEST/UAT and PROD have separate identities, config, secrets and data access. Config lives outside the artifact.

Approvals and identity

PROD needs approved human reviewers, configured on the GitHub environment. Use OIDC or workload identity where supported.

Traceability

Production, artifact, commit, PR, reviewer, CI result and deployment record stay connected.

How it starts

cd.yml runs on version tags (v*.*.*) or manual dispatch: build-once, then dev, test, production jobs in order.

Project overlay

bash scripts/deployment-hook.sh reports NOT CONFIGURED until your stack overlay supplies a deployment adapter.

16 — Rollback

When a deployment goes wrong

ProblemHuman approvalKnown-good release

What you do: if production health, security, data or behavior fails after a release, raise it to the incident lead or production owner. Once approved, redeploy the previous verified artifact rather than rebuilding, then validate and record the result. Fix the cause through the normal PR path afterwards.

  1. Identify the failed deploymentHealth, security, data integrity, availability or business behavior has failed.
  2. Assess impactDeclare an incident or change record and capture the current artifact and evidence. The incident lead or production owner decides on rollback.
  3. Roll back to the previous known-good artifactSelect it by manifest and digest (ROLLBACK_ARTIFACT, ROLLBACK_DIGEST), confirm config and data compatibility, get human emergency approval (ROLLBACK_APPROVED), then run bash scripts/rollback-hook.sh.
  4. ValidateCheck health, security, data integrity and user impact. Record result, approver and digest.
  5. Raise an incident or bugTrack it to a work item.
  6. Investigate the root causeFeed recurring causes into the learning loop.
  7. Fix, test, redeployUse the normal path: branch, PR, CI, review, merge, promote. A hotfix/ branch is for urgent incidents.
Rollback does not reverse data migrations. Plan a forward fix or an approved recovery. See docs/deployment/rollback.md. Emergency bypass of protections follows the break-glass procedure; the rollback hook itself is project-overlay specific.

18 — Exceptions

No silent bypasses

When

Only when a MUST requirement genuinely cannot be met, the reason is specific, and compensating controls reduce the risk. Never a permanent alternative to doing the work, and never for a committed secret.

Who decides

The owner for the area decides: repository maintainer, architecture, security, data, AI, platform or release owner. High and Critical need the accountable risk owner. An agent cannot approve an exception.

What to record

Use docs/adr/exception-template.md: exception ID, principle ID, reason, scope, risk, mitigation, owner, approver, created date, expiry or review date, evidence.

Expiry and review

Link the record and its expiry in the PR. Owners review open exceptions at least monthly. An expired exception is non-compliance until renewed by an authorized human.

Process: docs/governance/exceptions.md. Emergencies: break-glass procedure.

21 — Developer FAQ

Practical questions

What if I only change code?

Add or update unit tests, run bash scripts/check.sh, and open a normal PR. If the Baseline Guard reports no impact, the standard review applies. Code and tests are routed to the Code Quality and Architecture agents.

What if I change infrastructure?

Treat it as higher risk: disclose configuration and infrastructure impact in the PR, include rollback, and expect platform owner approval. The Baseline Guard may report BASELINE_IMPACT or ARCHITECTURE_CHANGE, which routes to the Security & DevOps and Architecture agents.

What if I change a prompt?

Complete the AI-specific impact section and provide evaluation evidence; model and prompt changes need the AI owner. A prompt-only change is not an architecture change unless it is a protected contract.

What if CI fails?

Read the failure message, which names the policy ID, fix the cause and push again. Do not disable or weaken the check. If it also fails on a clean main, tell the repository maintainer.

What if an agent finds an issue?

Treat it as evidence from a reviewer. Fix it, or record a disposition with a reason. A confirmed violation of a MUST needs a fix or an approved exception.

When do I need an ADR?

For a new service, external dependency, data store, public API, model or provider, RAG source, guardrail change, infrastructure pattern, security exception or breaking change, and whenever the Baseline Guard reports ARCHITECTURE_CHANGE. Not for normal feature work.

Can I bypass a check?

No. Use the exception process, or the break-glass procedure for an incident. Both are recorded and approved by humans.

Who approves production?

An explicit production approver, enforced through the PROD environment's required reviewers. Agents cannot approve production.

What happens when I need an architecture change?

Write an ADR with Baseline impact: change and the affected boundaries, ask the architecture owner to approve it, and expect specialist reviews. Editing docs/architecture/baseline.yaml also needs Baseline update: yes. The ADR requirement is enforced by CI once the baseline status is approved.

How do I onboard an existing project?

Follow the Brownfield path: assess against the policies, record findings and risk, build a remediation roadmap, and adopt progressively. Do not rebuild the project from the skeleton.
