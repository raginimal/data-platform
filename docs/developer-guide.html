01 / The foundation

A reusable delivery system, not an application

The AI Delivery Foundation is a technology-neutral repository skeleton for AI and data projects. It supplies the context, policies, review contracts, deterministic checks, and delivery hooks that a new project would otherwise have to invent.

Implemented

Repository context

AGENTS.md, README.md, CONTRIBUTING.md, SECURITY.md, AI_POLICY.md, and DATA_POLICY.md establish working rules and boundaries.

Implemented

Policies and governance

policies/ contains stable IDs for architecture, dependencies, DevOps, security, data, AI, agents, and repository controls. ADR and exception templates provide decision records.

Implemented

Checks and delivery hooks

scripts/ provides lint, test, security, validation, baseline, artifact, deployment, and rollback entry points. Stack-specific commands are overlays.

Know the boundary. Deterministic CI enforces checks. Advisory agents explain risks and recommendations. Human owners approve architecture, exceptions, risk acceptance, merges, and production.
Lock the architecture and engineering boundaries first; allow developers to implement features flexibly within those boundaries.
Architecture baselineApproved decisions and protected boundaries
Multiple engineers + CopilotIndependent feature development inside the baseline
Pull request + Baseline GuardDetect architectural drift and route review
CI + agents + human approvalEnforce rules, assess context, approve material changes
Lock as a shared baseline

Application architecture, component boundaries, approved technology, API and data contracts, AI integration, security and IAM, CI/CD, deployment, and ownership.

Keep flexible for developers

Internal implementation details, feature-specific coding choices, local names and helpers, prompts within controls, and normal features that respect the architecture.

02 / Start well

Set up and plan the project before coding

Greenfield setup

  1. Start from the foundation skeleton or a controlled copy of it.
  2. Run bash scripts/setup.sh and review PROJECT.yaml.
  3. Choose the language, project type, environments, owners, and cloud posture.
  4. Read the relevant policies before adding dependencies, data, models, or infrastructure.
  5. Set up protected main, CODEOWNERS, the PR template, and GitHub environments.

Plan the first slice

  1. Write the problem, intended users, unacceptable use, and success measures.
  2. Identify data classification, retention, trust boundaries, and accountable owners.
  3. Choose the smallest useful vertical slice and its acceptance tests.
  4. List architecture decisions that need an ADR or baseline review.
  5. Declare the policies, reviewers, and evidence the pull request will require.
Greenfield

Establish the baseline, policies, ownership, and CI controls before the first feature. The separate project then tests whether independent engineers, prompts, models, and implementation choices can work safely inside the boundaries.

Brownfield

Do not rebuild an existing application from the skeleton. Assess its repository, architecture, DevOps, security, data, and AI practices, then adopt the foundation progressively through a risk-ranked roadmap.

Operating decision: keep the reusable foundation focused on its current Phase 1-6 capabilities while the greenfield sample project provides evidence for future framework improvements. Do not add a new framework feature merely to support the sample project.

03 / The golden path

Move from idea to release through visible gates

Every feature follows the same shape. The artifacts change by project; the accountability model does not.

1

Establish

Architecture baseline and engineering boundaries

2

Develop

Multiple engineers and Copilot build features independently

3

Guard

PR and Baseline Guard detect protected-boundary changes

4

Review

CI, agents, CODEOWNERS, and specialist owners review

5

Approve

Humans approve architecture changes, risk, and merge

The normal feature PR is intentionally flexible. Different prompts, approved models, libraries, and implementation approaches are allowed when they respect the baseline. A protected architectural decision cannot be approved accidentally through an ordinary feature PR.
Implemented controls

Policy, quality, security, and CI workflows exist. The Architecture Baseline Guard classifies changes as NO_BASELINE_IMPACT, BASELINE_IMPACT, or ARCHITECTURE_CHANGE.

Conditional overlays

Stack-specific linting, tests, dependency scans, SAST, IaC, deployment, health checks, and model evaluations are enabled by the project overlay when applicable.

04 / Architecture

Lock boundaries, keep implementation flexible

The architecture baseline records the decisions that would be expensive or risky to change. It does not freeze every class name, query, or algorithm.

BoundaryWhat it locksWhat remains flexible
BL-APPApplication pattern and layeringModule internals and algorithms
BL-COMPMajor components, ownership, service contractsPrivate implementation behind a contract
BL-TECHLanguage, runtime, cloud and platform boundaryLibraries inside the approved platform
BL-DATAData stores and data contractsQueries and schemas within an approved store
BL-AI / BL-MODELAI integration pattern, provider and model boundaryPrompts, evaluations, tuning within the boundary
BL-SEC / BL-DEPLOYTrust, identity, deployment and promotion topologyLeast-privilege grants and sizing inside the model
BL-CICD / BL-REPOGates, artifact promotion, layout and ownershipStep implementation within the gates

When a boundary changes

Run bash scripts/validate-baseline.sh with a changed-file list. A normal change follows the regular PR path. A baseline impact names the affected agents and owners. An architecture change requires an ADR using docs/adr/template.md; once the baseline is approved, CI fails if the ADR metadata is missing.

Copilot prompt / architecture draft
Read ARCHITECTURE.md, docs/architecture/baseline.yaml, and the relevant policies. Draft a small architecture decision for [capability]. Identify the boundary IDs, alternatives, risks, tests, rollback path, and whether this is NO_BASELINE_IMPACT, BASELINE_IMPACT, or ARCHITECTURE_CHANGE. Do not edit files.
05 / Feature delivery

Use Copilot feature by feature

Understand

Ask Copilot to locate the owning module, nearby tests, policy IDs, and existing patterns before proposing code.

Specify

Turn the acceptance criteria into a small interface, failure cases, test cases, and evidence requirements.

Implement

Ask for the smallest change in the existing style. Keep generated code untrusted until reviewed and tested.

Verify

Run focused tests and scans first, then the complete bash scripts/check.sh gate before committing.

Review

Use the relevant specialist agent for findings, not approval. Resolve evidence-based issues and escalate decisions to owners.

Disclose

Record material AI assistance, changed policies, tests, risks, and reviewers in the pull request.

Copilot prompt / implementation slice
Inspect the requested feature, its owning abstraction, nearby tests, and applicable policies. State one falsifiable hypothesis about the change, one focused check that could disconfirm it, and the smallest implementation. Then make the edit and run that focused check.
Copilot prompt / test-first behavior
For [feature], list the observable behavior and failure cases. Add focused tests using existing repository conventions, implement only enough code to pass them, and report the exact validation command and result. Do not change unrelated files.
06 / Specialist review

Four agents, four lenses, one human boundary

The GitHub Copilot custom agents are read-only and advisory. They return evidence-based findings using the shared output contract; they cannot edit, merge, approve, waive, or deploy.

Routing is change-aware. config/ai/agent-routing.yaml provides default path routing, while the baseline guard adds agents named by an affected boundary. The matching agent reviews; the approval matrix decides who must approve.
Copilot prompt / specialist review
Review only the changed files for [area]. Read the relevant agent contract, policies, and tests. Return evidence-based findings in the repository's YAML finding format with severity, confidence, policy ID, file, evidence, recommendation, and human action. Do not edit files or approve the change.
07 / Delivery

Branch, prove, review, merge

Short-lived feature branches return to protected main through a pull request. Release tags identify approved commits; the delivery workflow builds once and promotes the same artifact through environments.

Feature work
feature/*->PR + checks->protected main
Release
tag v1.0.0->build once->DEV->TEST/UAT->PROD approval
Rollback
issue detected->human decision->previous digest->known-good PROD
Rollback rule: restore the previous verified artifact by manifest and digest, validate health and data behavior, record the approver, then fix the cause through the normal PR path. Data migrations require a forward recovery plan; rollback does not automatically reverse them.

Git and pull requests

  1. Start from current protected main.
  2. Use feature/<issue>-<name>, bugfix/..., or hotfix/....
  3. Use focused Conventional Commits where the stack permits.
  4. Keep the PR small, link the work item, and complete every applicable PR section.
  5. Declare architecture, security, data, AI, infrastructure, testing, and AI-assistance impact.

Local proof

bash scripts/check.sh

08 / Engineering practice

Good defaults for serious work

Keep changes smallMake work reviewable, reversible, traceable to an issue, and isolated from unrelated cleanup.
Make dependencies explicitDocument purpose, owner, license, provenance, update strategy, and vulnerability risk.
Validate at boundariesTreat repository content, external inputs, model output, and tool results as untrusted.
Protect dataClassify before processing. Minimize collection and retention. Use synthetic or de-identified test fixtures.
Never hide a failureFix failed checks or record why a check is not applicable; never disable a control to make CI green.
Build onceIdentify artifacts by commit and promote the same artifact. Keep rollback and post-deployment validation documented.
Use AI carefullyDo not send confidential, personal, regulated, production, credential, or proprietary data to an unapproved AI tool.
Keep models governedVersion models, prompts, retrieval sources, evaluations, guardrails, and safety settings; evaluate quality, latency, cost, and refusal behavior.
09 / Worked example

ai-data-platform: a local-first data project

This example shows how the Foundation turns an approved architecture into an implementation sequence. It is an architecture walkthrough, not an application implementation.

Approved project shape

Python + DuckDB + dbt

Python owns orchestration and input validation. DuckDB provides local persistence. dbt owns SQL transformations and produces manifest/catalog evidence. BigQuery remains a future provider overlay.

Future capability

Governed explanations

A later assistant will explain approved contracts, quality results, and lineage evidence. It will not query unrestricted raw data or take autonomous actions.

Copilot prompt / ai-data-platform slice
Work in the ai-data-platform architecture: Python orchestration, DuckDB local persistence, dbt SQL transformations, versioned data contracts, and dbt-artifact lineage. For [slice], inspect ARCHITECTURE.md and the relevant DATA, SECURITY, or AI policies. Propose the smallest testable change, name its baseline impact, add focused tests, and run the narrowest validation. Do not introduce BigQuery, a model provider, or new infrastructure unless an ADR and approved boundary require it.

When the project is ready for a real provider, the model identifier, data boundary, prompt, guardrails, evaluation set, cost controls, and human escalation path become reviewable AI assets. The provider is not treated as an invisible implementation detail.
